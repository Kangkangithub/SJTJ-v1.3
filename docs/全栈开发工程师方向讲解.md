# AI 加持下的全栈开发工程师：从「神农AI」看懂前后端

> 本文档以你手上的「神农AI」项目（前端 HTML/CSS/JS + Node.js/Express 后端 + Neo4j + SQLite + LangChain GraphRAG）为例子，讲清楚全栈开发的核心概念。适合初学者，尽量少用黑话。

## 0. 先建立一张「整体地图」

一个网页应用，本质就是三句话：

```
浏览器（用户看到的界面）
   │  发 HTTP 请求（比如「给我药材列表」「新增一味药」）
   ▼
后端服务器（Node.js + Express）
   │  查数据库 / 调 AI / 处理业务
   ▼
数据库（SQLite 存关系数据，Neo4j 存知识图谱）
```

你现在项目里的对应关系：

| 层 | 你的项目里是什么 |
|---|---|
| 前端（界面） | `frontend/` 下的 HTML + CSS + JS |
| 后端（逻辑） | `backend/` 下的 Express 应用 |
| 数据库 | `backend/data/herb-knowledge.db`（SQLite）+ 云端 Neo4j AuraDB |
| AI 能力 | `backend/src/services/ragServiceV2.js` 等 |

只要记住：**前端负责「看和问」，后端负责「查和算」，数据库负责「存」**。

## 2. 后端是什么：Node.js 和 Express 的关系

**Node.js**：让 JavaScript 能脱离浏览器、在服务器上运行的一个「运行环境」。没有它，JS 只能在浏览器里跑。

**Express**：跑在 Node.js 之上的一个「Web 框架」，帮你处理「收到什么请求 → 调用什么函数 → 返回什么响应」。

两者关系打个比方：

| 概念 | 比喻 |
|---|---|
| Node.js | 一台发动机 |
| Express | 装在发动机上的方向盘和档位 |

**没有 Express 也能写后端**（用 Node 原生 http 模块），但很麻烦；Express 帮你把「路由、请求解析、响应返回」这些重复劳动都封装好了。

你的后端入口在 `backend/src/app-simple.js`，它就是用 Express 搭起来的。

## 3. 核心概念 1：中间件（Middleware）

### 3.1 中间件是什么

**中间件 = 请求处理链上的一个个「关卡」**。

一个请求进来后，会**依次穿过**一串中间件，每个中间件可以做一件事，然后决定「放行」或「拦截」。

打个比方：**机场安检流程**。

```
请求（乘客）
  ↓
① 安检门（安全检查）      ← helmet 中间件
  ↓
② 查护照（验证身份）      ← auth 中间件
  ↓
③ 检查行李（数据校验）    ← validation 中间件
  ↓
④ 办理登机（真正干活）    ← 路由处理函数
  ↓
返回结果
```

### 3.2 你项目里真实用到的中间件

在 `backend/src/app-simple.js` 的 `setupMiddleware()` 里，按顺序挂了这些：

| 中间件 | 作用 | 通俗解释 |
|---|---|---|
| `helmet` | 安全防护 | 给响应加各种安全头，防常见 Web 攻击 |
| `cors` | 跨域 | 允许前端页面从不同端口访问后端 |
| `compression` | 压缩 | 把响应压小，传输更快 |
| `morgan` | 日志 | 每次请求打一行日志 |
| `express.json()` | 解析请求体 | 把前端发来的 JSON 字符串转成 JS 对象 |
| `express.static` | 静态文件 | 直接托管 HTML/CSS/JS/图片 |
| `rateLimit` | 限流 | 防止有人疯狂刷接口 |

你项目里还有两个「自定义中间件」在 `backend/src/middleware/`：

| 文件 | 作用 |
|---|---|
| `auth.js` | 验证登录（`authenticateToken`、`requireAdmin` 等） |
| `validation.js` | 用 Joi 校验请求数据（`validate(herbSchema)`） |

### 3.3 中间件代码长什么样

一个最简单的中间件就是「接收 req/res/next，处理完调 next() 放行」：

```js
// 一个记录时间的中间件（示例）
function logTime(req, res, next) {
  console.log('收到请求：', req.method, req.url);
  next(); // 放行，交给下一个关卡
}
app.use(logTime);
```

`next()` 是关键——不调用它，请求就卡住不动了。

## 4. 核心概念 2：Controller / Router / Service 分层

### 4.1 为什么要分层

一个接口如果只写在一个函数里，会变成「又接收请求、又查数据库、又算业务、又拼结果」的一坨代码，几百个接口就没法维护了。

所以后端普遍分成几层，**各司其职**：

```
请求进来
  ↓
Controller / Route   →  只负责「接请求、调 Service、返回响应」
  ↓
Service              →  只负责「业务逻辑」（算、查、组合数据）
  ↓
数据访问层           →  只负责「和数据库打交道」
```

### 4.2 你项目里的对应关系

**关键答案：你的项目其实也有 Controller，只是叫法不同。**

| 传统叫法 | 你项目里的文件 | 职责 |
|---|---|---|
| Controller | `backend/src/routes/*.js` | 接收 HTTP 请求、调用 Service、返回 JSON |
| Service | `backend/src/services/*.js` | 业务逻辑（RAG、知识图谱、用户等） |
| 数据访问 / Model | `backend/src/config/database-simple.js`、`neo4j-simple.js` | 连接 SQLite / Neo4j |

举例：`routes/herbs.js` 里的一个路由就是「Controller」：

```js
router.get('/', optionalAuth, async (req, res) => {
  // 1. 解析请求参数
  const { page = 1, limit = 20 } = req.query;
  // 2. 查数据库（数据访问）
  const db = databaseManager.getDatabase();
  // 3. 返回结果
  res.json({ success: true, data: ... });
});
```

所以：**Express 用 `routes/` 承担了 SpringBoot 里 `Controller` 的角色**。Express 不强制你建 controller 目录，但职责是一样的。

## 5. 核心概念 3：DTO 是什么，为什么 SpringBoot 用、这里不用

### 5.1 DTO 是什么

**DTO = Data Transfer Object，数据传输对象**。

就是「专门用来在不同层之间传数据」的一个「数据包装盒」，它只包含需要传递的字段，不含业务逻辑。

### 5.2 为什么 SpringBoot 用 DTO

Java / SpringBoot 是**强类型**语言，每个对象的字段、类型都是写死的。

问题来了：数据库里的「实体（Entity）」字段，往往**不该直接暴露给前端**。比如：

- 实体里有密码、内部 ID、审计字段，不能都发给前端
- 前端只需要「名称、分类、产地」，但实体有 20 个字段

于是 SpringBoot 里会单独定义 DTO 类，把「要传给前端的字段」重新包一层：

```java
// 实体（数据库映射，20 个字段）
class HerbEntity { Long id; String name; String pinyin; ... }

// DTO（只给前端看的 3 个字段）
class HerbDTO { String name; String category; String region; }
```

### 5.3 为什么你的 Express 项目没显式写 DTO

因为 **JavaScript 是弱类型**：

- 前端发来的 `req.body` 本身就是 JS 对象，想用哪个字段直接用
- 返回 `res.json({...})` 时，也是随手拼个对象

所以小项目里常常「省略」了 DTO 这一步，直接传对象。

**但 DTO 的思想你项目里其实也有**，只是换了形式：

| SpringBoot 里的概念 | 你项目里的对应物 |
|---|---|
| DTO（定义字段） | `middleware/validation.js` 里的 Joi schema（规定字段和类型） |
| 字段裁剪 | `normalizeHerb()` 这类函数（把数据库原始数据整理成前端要的格式） |

> 结论：**不是「不需要」，而是 JS 项目用更轻的方式实现了同样的目的。** 项目变复杂后，很多 Express 项目也会显式引入 DTO / 类型定义。

## 6. 核心概念 4：API 通信（HTTP / RESTful）

### 6.1 前端怎么和后端说话

前后端分离后，它们只通过 **HTTP 请求** 交流。一次对话长这样：

```
前端 fetch('http://localhost:3001/api/herbs')
  ↓ 发一个 GET 请求（带 URL、请求头）
后端收到，查数据库
  ↓ 返回一个响应（带状态码 + JSON 数据）
前端拿到 JSON，渲染到页面
```

### 6.2 最常用的四种 HTTP 方法（就是 CRUD）

| 方法 | 含义 | 对应操作 | 你项目的例子 |
|---|---|---|---|
| GET | 读 | 查询 | 获取药材列表 `GET /api/herbs` |
| POST | 增 | 新建 | 新增药材 `POST /api/herbs` |
| PUT | 改 | 更新 | 修改药材 `PUT /api/herbs/:id` |
| DELETE | 删 | 删除 | 删除药材 `DELETE /api/herbs/:id` |

这就是 **CRUD**（Create/Read/Update/Delete）。

### 6.3 状态码是什么

服务器每次响应都会带一个「状态码」，告诉前端结果：

| 状态码 | 含义 |
|---|---|
| 200 | 成功 |
| 201 | 创建成功 |
| 400 | 请求有问题（参数错了） |
| 401 | 没登录 |
| 403 | 没权限 |
| 404 | 找不到 |
| 500 | 服务器内部出错 |

你之前遇到的 `400 Bad Request`、`500 Internal Server Error`、`404 Not Found`，就是这些状态码。

## 8. 完整链路：用户在网页上「新增一味药材」

以最典型的 CRUD「新增」为例，从点击按钮到数据入库，一步一步走：

```
① 用户在前端表单填好「药材名、分类、产地…」，点【保存】

② 前端 js/herb-manage.js 发请求
   fetch('http://localhost:3001/api/herbs', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({ name: '人参', category: '补虚药', ... })
   })

③ 后端 app-simple.js 收到请求，先穿过中间件链：
   helmet → cors → morgan → express.json()（把 JSON 字符串转成 req.body 对象）

④ 命中路由 routes/herbs.js 里的：
   router.post('/', authenticateToken, requireAdmin, validate(herbSchema), async (req,res) => {
     ...
   })
   依次执行：
   - authenticateToken：检查是否登录
   - requireAdmin：检查是不是管理员
   - validate(herbSchema)：用 Joi 校验字段是否合法

⑤ 路由处理函数里：
   调用 databaseManager（SQLite）执行 INSERT 语句，写入数据库
   （如果涉及图谱，还会调 neo4j 执行 Cypher）

⑥ 返回响应：
   res.status(201).json({ success: true, data: { id: 新ID, name: '人参' } })

⑦ 前端收到 201 和 JSON，刷新列表、弹出「保存成功」
```

**一句话总结链路**：
`前端 fetch → 中间件链 → 路由（Controller）→ Service/数据库 → 返回 JSON → 前端渲染`

## 9. 学了 JS 后端，能迁移到其他后端技术栈吗？

**能，而且比你想象的好迁移。**

因为**后端开发的「思想」是通用的，只有「语法和框架」在变**。下面这些你在这项目里已经接触过的概念，到任何后端都成立：

| 通用概念 | Express 里 | SpringBoot 里 | Django 里 |
|---|---|---|---|
| 路由/Controller | `routes/*.js` | `@Controller` 类 | `views.py` |
| 中间件 | `app.use()` | `Filter` / `Interceptor` | `Middleware` |
| 数据校验 | Joi schema | DTO + Validation | Serializer |
| 数据库访问 | 直接 SQL / driver | MyBatis / JPA | ORM |
| 认证 | JWT 中间件 | Spring Security | Django Auth |
| 错误处理 | 中间件 | `@ControllerAdvice` | `handler` |

**相同的底层原理**：
1. HTTP 协议、REST 设计、状态码、请求/响应格式——完全一样
2. 分层思想（Controller/Service/数据访问）——完全一样
3. 数据库、SQL、缓存、认证、中间件——概念一样

**要新学的只是**：
- 语言语法（Java 的类、类型；Python 的语法）
- 框架的 API 写法（注解 vs 装饰器 vs 中间件）

> 结论：你现在学的不是「Express」，而是「后端开发的通用套路」。换 SpringBoot / Django / Go，只是换个语法把同一套套路再写一遍。

## 10. TypeScript vs JavaScript：我落后了吗？

**没有落后，你现在写的是「基础」，TypeScript 只是在这个基础上加了一层「类型」。**

### 10.1 区别是什么

| | JavaScript | TypeScript |
|---|---|---|
| 类型 | 弱类型（变量可以是任何类型） | 强类型（写死类型，编译期检查） |
| 例子 | `let name = '人参'` | `let name: string = '人参'` |
| 报错时机 | 运行时才发现错误 | 写代码时就报错 |

### 10.2 为什么现在很多项目用 TypeScript

1. **类型检查**：写错字段名、传错类型，编辑器立刻标红，不用等运行才炸
2. **更好协作**：类型就是「活文档」，别人一看就知道数据长什么样
3. **大型项目好维护**：项目越大，类型越能救命

### 10.3 你现在的状态

你项目是 **纯 JavaScript**，这在小项目、快速开发、演示答辩场景完全够用，**不是落后**。很多公司的小型服务、脚本、工具也还是纯 JS。

**正确的心态**：先把 JavaScript 本身学扎实（尤其是对象、函数、异步 `async/await`），然后再学 TypeScript 会非常快——因为 TS 就是「JS + 类型」，核心还是 JS。

## 12. Redis 是什么，你的项目需要吗

### 12.1 一句话解释

**Redis 是一个「内存数据库」**：数据直接放在内存里，读写极快，常用来做**缓存、会话、限流、排行榜**。

### 12.2 和 SQLite / MySQL 有什么区别

| | SQLite / MySQL | Redis |
|---|---|---|
| 数据放哪 | 磁盘（能长期保存） | 内存（快，但重启可能丢） |
| 速度 | 较慢 | 极快（毫秒级） |
| 典型用途 | 存业务数据（药材、用户、对话） | 缓存、临时数据、会话 |

### 12.3 Redis 最常见的 5 个用途

1. **缓存**：把查过的结果存 Redis，下次直接返回，不查数据库
2. **会话 Session**：多台服务器共享登录状态
3. **限流**：统计请求次数，防止刷接口
4. **排行榜 / 计数**：点赞数、访问量
5. **消息队列**：异步处理任务

### 12.4 你的项目现在需要 Redis 吗？—— **暂时不需要**

理由很实在：

1. **你是单机单进程运行**，不存在「多台服务器要共享数据」的问题
2. **你已经有了「进程内缓存」**，效果类似 Redis 的单机版：
   - `routes/herbs.js` 里的 `routeCache`（Map，10 分钟缓存）
   - `herb-pages.js` 里的 `apiCache`
   - RAG 的「5 分钟答案缓存」
3. **数据量小**：275 味药材，SQLite 查询足够快，没到需要缓存加速的地步
4. **对话历史存 SQLite**，单机完全够用

### 12.5 什么时候才需要引入 Redis

等你走到下面这些阶段，再引入不迟：

1. 部署成**多实例 / 集群**（多个后端进程要共享缓存和会话）
2. **用户量、并发量**上来，数据库查询成为瓶颈
3. 需要**分布式限流**（多台机器一起统计请求次数）
4. 未来「用户数据隔离 + 多用户大规模上线」时

### 12.6 结论

> **现在不用加，但要理解它解决什么问题。** 等真正多用户、多实例时，把现在的「进程内 Map 缓存」换成「Redis」即可，业务逻辑基本不用动。

## 13. 前端存储三兄弟 + sessionStorage + AI 对话历史

### 13.1 Web Storage 三兄弟对比

| | localStorage | sessionStorage | cookie |
|---|---|---|---|
| 生命周期 | **永久**（除非手动删） | **关标签页就没了** | 可设过期时间 |
| 容量 | ~5MB | ~5MB | ~4KB |
| 共享范围 | 同源所有标签页共享 | **每个标签页独立** | 同源 |
| 自动发给服务器？ | 否 | 否 | **是**（每次请求自动带） |

### 13.2 你项目的实际用法

- **登录 token** 和 **userInfo**：存 `localStorage`（这样关掉浏览器再打开，登录状态还在）
- **AI 对话历史**：存**后端 SQLite**（`conversations` + `messages` 表），登录后跨设备都能看到

> 所以你现在**没有用 sessionStorage**，用的是 localStorage + 后端数据库，这是正确且常规的做法。

### 13.3 sessionStorage 适合什么场景

`sessionStorage` 的特点是「**关标签页就自动清除，且每个标签页互不干扰**」，适合：

- 未登录时的**临时对话**
- 表单**草稿**（刷新不丢，关页面清空）
- 单个页面的**临时标记**

### 13.4 AI 对话历史该怎么存（三种选择）

| 需求 | 存哪里 | 特点 |
|---|---|---|
| 刷新就没了 | 内存变量 | 最简单，页面一刷新全丢 |
| 同标签页刷新不丢、关页面就丢 | **sessionStorage** | 轻量临时会话 |
| 登录后跨设备、永久保留 | **后端数据库**（你项目用 SQLite） | 可靠、可多端同步 |

你之前做过的「**不离开网页时保留历史、关闭网站再打开就没了**」那种需求，本质就是 `sessionStorage` 的典型应用场景。

### 13.5 结论

- 你现在：`token → localStorage`、`对话 → 后端 SQLite`，是标准做法 ✅
- 想「临时对话不留痕」→ 用 `sessionStorage`
- 想「永久历史 + 多端同步」→ 用后端数据库（你已经做了）

## 14. 深入拆解：你的「核心渲染器」是怎么工作的

你在文档前面看到的 `herb-pages.js`，本质上做了两件事：**渲染（把数据画成页面）+ 请求数据（从后端拿数据）**。这一章把它拆开讲透。

### 14.1 先看 render() 函数（渲染）

```js
function render() {
  const hero = getHero();
  document.title = `${hero.title} - 神农AI`;
  app.innerHTML = `
    <div class="page-shell">
      ${renderTopbar()}
      <main>
        ${renderHero(hero)}
        ${renderPage()}
      </main>
      ${renderFooter()}
    </div>
  `;
  bindEvents();
}
```

逐行理解：

1. `render()` **不查任何数据**，只负责「把当前 `state` 画出来」
2. `app.innerHTML = ...` 用**模板字符串**（反引号 ` 包裹）拼出一整页 HTML，一次性塞进 `#app` 容器
3. `${renderTopbar()}` 这些是「调用子渲染函数」，每个子函数返回一段 HTML 字符串
4. `renderPage()` 会根据 `state.page` 决定画「首页 / 查询页 / 图谱页 / 推荐页」
5. 最后 `bindEvents()` 重新给按钮绑定点击事件（因为页面被整体替换了，旧事件会失效）

> 关键点：**render 是「纯画」，数据从 `state` 读，不发起请求。**

### 14.2 数据加载的「三步曲」

页面一打开，执行的是 `init()`：

```js
async function init() {
  render();                    // ① 先画一个空骨架（还没数据）
  await hydrateBaseData();     // ② 加载基础数据（分类、地区、统计、方剂）
  await hydratePageData();     // ③ 加载当前页面专属数据（药材列表/图谱/推荐）
  state.loading = false;
  render();                    // ④ 数据齐了，再重新画一次完整内容
}
```

为什么 `render()` 调了**两次**？

- 第一次：页面刚打开，数据还没回来，先画个「骨架」让用户看到界面
- 第二次：数据都加载完了，把真实数据填进去再画一次

这就是「**先渲染骨架 → 请求数据 → 再渲染完整内容**」的经典套路。

### 14.3 基础数据用 Promise.allSettled 并行加载

`hydrateBaseData()` 里，4 个接口是**同时发**的：

```js
const [categories, regions, stats, formulas] = await Promise.allSettled([
  apiGet('/api/herb-categories'),
  apiGet('/api/herb-regions'),
  apiGet('/api/herbs/statistics'),
  apiGet('/api/formulas?limit=100')
]);
```

- `Promise.allSettled` 让 4 个请求**并行**跑，等**全部结束**（不管成功失败）再继续
- 返回一个数组，每个元素是 `{ status, value }` 或 `{ status, reason }`
- 后面逐个判断 `if (categories.status === 'fulfilled')` 才把结果写进 `state`

> 为什么不用 `Promise.all`？因为 `Promise.all` 遇到一个失败就整体失败；而这里希望「即使统计接口挂了，药材列表也要正常显示」，所以用 `allSettled`。

### 14.4 renderPage 是「分发器」

```js
function renderPage() {
  if (state.page === 'home') return renderHome();
  if (state.page === 'search') return renderSearch();
  if (state.page === 'graph') return renderGraph();
  // ...
}
```

它根据 `state.page`（来自 HTML 的 `data-page` 属性）决定调用哪个「页面渲染函数」。这就是你项目的「迷你路由」。

## 15. 为什么流行 SPA？Vue 怎么做？你的项目怎么做？

### 15.1 什么是 SPA

**SPA = Single Page Application，单页应用**：整个网站只有一个 HTML 页面，切换页面**不刷新浏览器**，靠 JS 动态替换内容。

### 15.2 SPA 的好处

1. **切换快、体验顺**：不用重新加载整个页面
2. **前后端彻底分离**：前端只管界面，后端只管数据接口
3. **只加载一次框架**，之后只请求数据

### 15.3 Vue 是怎么实现 SPA 的

Vue 靠三个核心能力：

| 能力 | 作用 |
|---|---|
| **响应式** | 数据一变，界面**自动**更新，不用手动调 render |
| **虚拟 DOM** | 高效算出「哪里变了」，只更新变化的部分 |
| **组件** | 每个 UI 块（按钮、列表、弹窗）是一个独立 `.vue` 组件 |
| **Vue Router** | 根据 URL 显示不同组件（页面切换） |

### 15.4 你的项目：手写的「类 SPA」

你的项目没有用 Vue，但**思路和 Vue 一样**，只是全部手写：

| 能力 | Vue | 你的项目 |
|---|---|---|
| 页面切换 | Vue Router | 多 HTML + `data-page` 属性 |
| 响应式 | 自动更新 | 手动调 `render()` |
| 组件 | `.vue` 文件 | 一个个 `renderXxx()` 函数 |
| 数据存储 | Pinia | `state` 对象 |

**你的 `herb-pages.js` 相当于「手写了一个 mini Vue」**：有 state、有 render、有页面分发，唯一区别是 Vue 数据变了自动渲染，你要手动调 `render()`。

这就是为什么上一轮我们说它是「类 SPA / 手写框架」——你已经理解并实现了 SPA 的核心思想，只是没有用现成框架。

## 16. 异步 async/await 与 Promise 详解

### 16.1 为什么需要「异步」

网络请求要等服务器响应（几十到几百毫秒）。如果「同步等待」，页面会**卡死**，用户点什么都动不了。

所以要用**异步**：发出请求后先不傻等，等响应回来了再继续处理。

### 16.2 Promise 的三种状态

Promise（承诺）有三种状态，**状态一旦改变就固定，不可逆**：

```
        pending（进行中）
         /        \
   成功 /          \ 失败
      ▼            ▼
 fulfilled（已完成）  rejected（已拒绝）
 拿到结果 value      拿到原因 reason
```

- `pending`：还没出结果
- `fulfilled`：成功，拿到 `value`
- `rejected`：失败，拿到 `reason`（错误原因）

### 16.3 async/await 是什么

- `async function`：声明这是「异步函数」，**它返回的一定是 Promise**
- `await`：**等待一个 Promise 完成并拿到结果**，只能写在 async 函数里

### 16.4 对比旧写法 .then()

```js
// 旧写法：.then() 链，层层嵌套，容易乱
fetch(url)
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => console.error(err));

// 新写法：async/await，从上往下读，像同步代码一样直观
async function getData() {
  try {
    const res = await fetch(url);     // 等响应
    const data = await res.json();    // 等解析成 JSON
    console.log(data);
  } catch (err) {
    console.error(err);               // 失败统一在这处理
  }
}
```

`async/await` 就是 `.then()` 的「语法糖」——本质一样，但更易读。

### 16.5 你项目里的真实例子

**例子 1：apiGet（发请求）**

```js
async function apiGet(path) {
  const response = await fetch(url);   // ① 等网络响应回来
  const json = await response.json();  // ② 等响应体解析成 JS 对象
  return json;                         // ③ async 函数自动把返回值包成 Promise
}
```

**例子 2：loadHerbs（请求 + 错误处理）**

```js
async function loadHerbs(options = {}) {
  try {
    const response = await apiGet(`/api/herbs?${params}`); // 等数据回来
    state.herbs = normalizeHerbs(response.herbs);          // 数据到了，更新 state
  } catch (error) {
    state.herbLoadError = true;  // 失败（rejected）走这里，标记错误
  }
}
```

**例子 3：Promise.allSettled（并行等待多个）**

```js
const [a, b, c, d] = await Promise.allSettled([p1, p2, p3, p4]);

// 判断每个是成功还是失败
if (a.status === 'fulfilled') {
  console.log('成功，结果：', a.value);
} else {
  console.log('失败，原因：', a.reason);
}
```

### 16.6 三个最常见的坑

1. **忘了 await**：拿到的是 Promise 对象，而不是数据本身
2. **忘了 try/catch**：请求失败（rejected）时没人接住，程序报错
3. **循环里用 await**：会变成「一个接一个」串行执行，慢；应改用 `Promise.all`

---

> 总结这一大段：**你的项目 = 手写版 SPA（state + render + 分发）**；**异步 = Promise（三状态）+ async/await（更好读的写法）**。把这两个吃透，再去看 Vue 的响应式，就是「从手动渲染升级到自动渲染」这一步。
